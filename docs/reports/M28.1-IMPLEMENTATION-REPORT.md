# M28.1 — Implementation Report: Runtime Decoupling & Performance Baseline

Status: **IMPLEMENTED, uncommitted**. All changes are additive except two
guarded behavior extensions; full serial gate results below.

## 1. Changed files

**Phase A — runtime decoupling (prove + lock, no manifest surgery):**
- `tests/cli-runtime-decoupling.test.ts` (new): walks every engine/CLI
  source dir and rejects imports of `three`, `react`, `src/ui/*`,
  `apps/web`, and browser globals. This is the enforcement mechanism —
  the CLI runtime path loads only what its import graph reaches.
- Manifest decision (documented, no change): root `package.json` keeps
  `three` because root `tsc` still compiles the preserved
  `src/ui/island3d/`; `apps/web/package.json` already owns its own copy.
  Removal becomes safe only at the UI-removal milestone. Verified: zero
  imports from `src/{cli,core,orchestrator,workers,workspaces,
  verification,dag,triage,claims,planner,config,db,git,benchmark}`
  into UI code.

**Phase B — per-project state isolation:**
- `src/config/state.ts` (new): `resolveDatabaseUrl()` precedence —
  explicit `DATABASE_URL` > nearest `.atlas/atlas.db` walking up from
  cwd (file must exist; bare dirs never redirect) > legacy
  `file:./dev.db`. Plus `resolveExplicitStateDir()` (mkdir harmless;
  missing DB file → actionable error naming the exact `prisma db push`
  provisioning command, never silent provisioning).
- `src/config/index.ts`: `loadConfig(env, {cwd}?)` resolves via the
  above; new `stateSource` field (`env|project|legacy`). Empty-string
  `DATABASE_URL` keeps its historical meaning (invalid, rejected) —
  existing `config.test.ts`/`doctor.test.ts` contracts preserved.
- `src/db/client.ts`: singleton passes the resolved URL via
  `datasourceUrl`. With no env and no `.atlas/` above cwd this resolves
  to the legacy file — byte-identical behavior.
- `src/cli/init.ts` + `src/cli/index.ts`: new `--state-dir <dir>` flag
  (dedicated client, ambient singleton untouched); init output reports
  `state: <url>` (human + JSON, additive only).
- `src/cli/doctor.ts`: Configuration line now shows
  `db=… (state: env|project|legacy)`.
- `tests/state-isolation.test.ts` (new): resolution unit tests
  (env-wins, legacy fallback, walk-up, bare-dir ignore, missing-file
  error) + two real repositories with `db push`-provisioned DBs proving
  disjoint projects/features and per-cwd resolution.

**Phase C/D:** no source changes (ad-hoc harness in `/tmp`, uncommitted).

## 3. Baseline measurements (deterministic; stub agent, trivial tests)
Environment: this machine, 3-task sequential chain, `node` stub agent
that writes+commits one file, `scripts.test: node pass.js`. Provider
latency is exactly zero — every figure below is Atlas + git + SQLite:

| Operation | Median/wall | Notes |
|---|---|---|
| `atlas --help` | 153 ms (n=5) | Node startup + commander parse |
| `atlas doctor` | 257 ms (n=5) | + git/docker probes + SELECT 1 |
| `atlas init` | ~185–232 ms | validate repo + 3 row writes |
| `atlas plan` (3 tasks) | ~179–202 ms | validate + persist + preview |
| `atlas run` e2e (3 seq tasks) | ~3.1 s (3 runs: 3082/3090/3075) | worktree×3 + spawn×3 + tests×3 + verify×3 + train |
| Per task inside run | worker ~265 ms, verify ~130 ms | from run `--json` stage fields |
| Scheduler | 0–2 ms/round (`schedulingMs`) | negligible, as suspected |
| Raw `git worktree add/remove` | 44 ms / 24 ms | git's share, not Atlas's |

Read: scheduler overhead is confirmed negligible; per-task cost is
spawn+test+verify subprocesses (~400 ms/task here); end-to-end is
dominated by wave count × per-task cost, and in production by provider
latency + the target repo's own test suite (both excluded here by
design — see limitations).

## 4. Limitations (no fabrication)
- Stub agent + `pass.js` tests: measures Atlas overhead only. Real runs
  add provider minutes and real test-suite minutes on top.
- Single machine, warm caches, n=3 for e2e (stable to ±1%: 3075–3090).
- SQLite on local disk; no concurrency contention measured (default
  `--max-concurrency 4`, sequential chain exercised waves 1-wide).
- Startup figures include first-Prisma-engine-load effects; cold-start
  (first ever engine unpack) not measured.

## 5. Migration / compatibility
- Default behavior is unchanged: no env + no `.atlas/atlas.db` above cwd
  → legacy `prisma/dev.db`, same as every prior milestone. Existing
  installs cannot silently lose data (the walk-up only triggers on an
  actually provisioned file).
- `AtlasConfig` gains `stateSource` (additive; zod default keeps old
  payloads valid). `init` JSON gains `stateDatabaseUrl` only with the
  flag. Doctor detail line changed textually (no test asserted the old
  string — verified).
- `getPrismaClient` now passes `datasourceUrl` explicitly; resolution is
  pure and side-effect-free. Tests constructing their own clients are
  unaffected.
- Schema provisioning for new project DBs remains an explicit operator
  step (`prisma db push`, dev tooling) — M28.2 item: a migrations-based
  provisioner for bare installs (no new infra, just wiring).

## 6. Full-gate result
Serial gate (`--pool=forks --maxWorkers=1`): **618/620 pass**. The 2
failures are timeouts in `benchmark-evolving-success` (180s) and
`verification-mergetrain` (30s) — files untouched by this milestone —
and both pass in isolation afterwards (7/7 in 87s, 16/16 in 36s). Same
load-flake signature as the M27.3 gate (which took 420s; this run took
1685s under contention). No failure touches config, db client, init,
decoupling, or state resolution.
