# M28.2 — Performance Report: Instrumentation & Benchmarking

Status: **IMPLEMENTED, uncommitted**. No orchestration semantics changed;
all additions are timing fields and reporting. Full-gate result in §8.

## 1. Methodology
- Stub agents only (`tests/fixtures/script-agent.mjs --write/--commit`,
  `/tmp/stub-agent.sh` for CLI runs) + trivial repo tests
  (`node -e process.exit(0)`): provider latency is exactly zero, so every
  figure is Atlas + git + SQLite. Real providers add minutes on top —
  that split is the point, not a limitation to apologize for.
- Temp git repos + `prisma db push` temp DBs (established test pattern);
  nothing measured touches the developer's project or `prisma/dev.db`.
- Medians of 5 where stated; single-run wall otherwise. Machine: this
  workstation, warm caches unless noted.

## 4. Analysis
**A. Measured bottlenecks:** per-task subprocess execution dominates —
worker spawn+exec (~265ms even for exit-0 stubs; real agents: minutes),
repo test suites (~130ms here; minutes in real repos), one worktree
add per task (~44–190ms observed range), one train integration per
wave(s). Scheduler: 0–2ms/round — negligible, confirmed twice.
**B. Likely but unmeasured:** real-provider latency distribution;
large-repo test suites; cold-start first engine unpack; SQLite
contention at high concurrency (default 4, waves here ran ≤3 wide).
**C. Atlas-controlled:** spawn/exec orchestration, worktree lifecycle,
test invocation, verification diffs, train commits, scheduling, DB
writes. **D. External:** provider model latency, repo test duration,
git binary speed, disk.
**E. Ranked candidates (impact × risk, evidence-gated):**
1. P1 — batch per-round scheduler input reloads (evidence: 0–2ms/round
   today → do NOT implement on this evidence alone; revisit only if a
   100-task profile moves it).
2. P1 — reuse worktrees across waves within a run (evidence: ~44ms/add
   × tasks; needs validation that reuse preserves isolation guarantees).
3. P2 — parallelize test execution with provider execution overlap
   (architectural; changes wave semantics — explicitly out).
4. P2 — keep-alive agent processes (kills process-group isolation
   model — rejected pending a security design).

## 5. M28.1 baseline comparison
Same 3-chain shape: M28.1 3075–3090ms vs M28.2 harness 4077–4100ms.
The delta is harness shape, not regression (CLI-subprocess per command
+ JSON parse + separate init/plan invocations vs in-process M28.1
script). Scheduling still 0–2ms; per-task worker/verify unchanged.
No speed claims made; the comparison is apples-to-oranges by construction
and labeled as such.

## 6. Limitations
- Stub agents + trivial tests: overhead-only lens by design.
- n=1–3 per e2e shape; warm caches; single machine; sequential + ≤3-wide
  waves only; no contention profile; no cold-start number.
- Harness asserts generous sanity bounds (10–180s), never tight perf
  gates — timing assertions must not flake CI.

## 7. Proposed M28.3 scope
Profile, don't optimize: (1) 100-task synthetic e2e to test whether
scheduler input reloads stay negligible; (2) 4-wide parallel e2e for
contention signal; (3) cold-start measurement protocol. Optimization
work (worktree reuse or otherwise) only with a profile in hand.
