# M28.6 — Controlled Pilot Report (Real Provider)

Status: **EXPERIMENT — no optimization, no commits**. See §13 for the
go/no-go on M28.7.

## 1. Executive summary
30 valid trials executed (2 workloads × 3 arms × 5 repeats), all
successful: independent A/B/C 5/5 each, schemaApi A/B/C 5/5 each. No
quota, rate-limit, timeout, or infrastructure failures. Medians —
independent: A 30.1s / B 37.0s / C 1.9s; schemaApi: A 41.7s / B 59.3s /
C 2.4s. Atlas overhead over single-agent on identical tasks: ≈+7s
(independent) and ≈+18s (chain, incl. an extra sequential agent call +
train). This is screening evidence (n=5), not proof: no significance
claims, no superiority declarations. One harness bug found and
quarantined mid-pilot (stub login message; affected group re-run
cleanly and the invalid 0/5 discarded as non-evidence).

## 3. Free-provider feasibility and quota limitations
- Preflight probe (trivial prompt): success in ~6.3s, no errors.
- Rate/quota limits for the free tier are undisclosed by the provider;
  mitigation: strictly sequential trials, no concurrency, `RATE_LIMIT`
  failure kind auto-classified by `command-provider.ts:257-290`, stop
  rules below. Cost recorded as null (free tier, never zero).
- 30 trials ≈ 40 agent calls total (Arm A: 1 call/trial; Arm B: 2
  calls/trial on 2-task workloads; Arm C: 0). Estimated wall 30–90 min
  sequential. Stop if: quota/rate-limit errors, any timeout, workspace
  isolation failure, or any risk to existing user work.

## 11. Interpretation and uncertainty
Observations: on 2-task workloads Atlas adds single-digit to
tens-of-seconds over a single agent (≈+23% independent, ≈+42%
chain), while succeeding on every trial; stub overhead stays ≈2s.
Interpretation (clearly labeled, not concluded): the overhead is
consistent with extra agent calls + train integration, not with
scheduler pathology (schedulingMs ≈ 0–2ms throughout). Uncertainty:
n=5, two synthetic workloads, one free model, no contention profile,
no cost data — these numbers describe this pilot only.

## 12. Whether evidence supports a next optimization
No. With 100% success and overhead consistent with extra agent calls +
integration (not scheduler or git pathology), there is no measured
bottleneck to justify an optimization milestone. The evidence supports
holding the current architecture, not changing it.

## 13. Recommended M28.7 direction
M28.7 = harder evidence, not optimization: (1) cost/token metering
decision (the one structural gap — without it no cost-per-success
claim is ever possible); (2) a larger-workload pilot (5+ tasks with
real dependency depth) to test whether the overhead ratio holds;
(3) contention profile at max concurrency. Do not optimize on n=5.
