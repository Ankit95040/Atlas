## 3. Actual execution architecture (command → completion)

### 3.1 Startup and state location (measured facts, not assumptions)
- **DB path is checkout-fixed, not project-local.** `loadConfig`
  (`src/config/index.ts`) defaults `DATABASE_URL` to `file:./dev.db`,
  which Prisma resolves relative to `prisma/schema.prisma` — i.e. always
  the Atlas checkout's `prisma/dev.db`, regardless of cwd. There is no
  `.atlas/` config file, no upward discovery, no `--db` flag.
  Consequence: running Atlas "inside arbitrary Git repositories" today
  still funnels all orchestration state into one SQLite file in the
  Atlas repo (plus `.atlas/` worktrees/train dirs created **inside the
  target repo** by default). Multi-project isolation is by row, not by
  file. Any CLI-first direction must decide the state-home story first
  (M28.1 scope item 1).
- **Singleton Prisma client** (`src/db/client.ts`); SQLite; no pooling
  layer; no Redis (never existed — AGENTS.md explicitly forbids it).
- **Startup overhead is unmeasured.** Node ≥20 + `dist/` plain JS; no
  bundling, no framework init on the CLI path. tsc output is committed
  as build artifacts (`dist/`, gitignored). No startup timing exists —
  measurement gap.

### 3.2 Per-task execution path (`runOneTask`, `run-loop.ts:479`)
Per task, in order: `createApproval` + `decideApproval` (2 DB writes) →
`assignTaskToWorker` (`git worktree add`, no copying — `git/worktree.ts:151`;
workspace row + `mkdir -p`) → provider `spawn` of the agent CLI
(`workers/command-provider.ts:186`, process-group kill semantics) →
`runTests` (`execFile` of `scripts.test` or `--test-command`) →
`verifyExecution` (git diff reads, never provider self-report) →
`transitionTask`. Wave barrier: next wave starts only after prior train
integration resolves (evolving) or all waves complete (original).
- **Dominant cost by construction: provider (agent) wall-clock**, then
  the repo's own test suite. Everything else is local subprocess + SQLite.
- **No background polling in the orchestrator.** Rounds are driven by
  `Promise.all` over the wave's `runOneTask` promises; re-planning per
  round is pure `planSchedule` over reloaded rows. Polling exists only in
  UI layers (2.5s island / 5s workspace), which die with the UI.
- **Per-round scheduler input reload** (`loadSchedulerInput` at
  `run-loop.ts:137,177`) re-reads tasks/workers/edges every round —
  O(rounds × graph). Suspected (not measured) minor cost; batching is a
  P1, not a P0.
- **Per-task git subprocess count is unmeasured.** Candidates: worktree
  add, base-commit resolve, diff reads (verify), train commits, worktree
  prune. Each is one `execFile("git", …)` (~5–15ms local). Count per task
  is unknown — measurement gap, likely small vs agent minutes.

### 3.3 Concurrency and limits
- Wave width bounded by `--max-concurrency` (default 4); worker pool is
  pre-created IDs consumed per round (`poolCursor`); pool exhaustion
  throws rather than queues (`run-loop.ts:189`). No unlimited workers
  (matches AGENTS.md). No timeouts on git/test spawns except
  `--agent-timeout-ms` on the provider.

## 4. Measured bottlenecks versus hypotheses

**Measured (in-tree evidence):**
- M17 parent findings (quoted in `docs/experiments/M18_SCALE_CROSSOVER_DESIGN.md:4-5`):
  SINGLE_AGENT 55/60 vs ATLAS_EVOLVING 51/60 (p≈0.26, n.s.), **AE median
  latency +40% vs single-agent**, 0 integration conflicts. The +40% is a
  real measured overhead number for the benchmark workloads of that
  generation — but its decomposition (agent retries? waves? verify?
  tests?) is **not recorded**.
- The orchestrator already emits per-stage timings:
  `schedulingMs[]` per round, `workerMs` and `verificationMs` per task
  (`run-loop.ts:181-183,505-531`), aggregated by the scale runner
  (`runner.ts:600-602`). These exist as fields, but no current report
  turns them into a bottleneck ranking — analysis gap, not data gap.
- Benchmark harnesses measure **wall-clock only**
  (`real/runner.ts:140,312`, `scale/runner.ts:58-83`); the scale design
  doc itself discloses that provider latency/token cost are unavailable
  and wave counts proxy for cost (§M18 doc lines 234-236, 250).

**Hypotheses (explicitly unmeasured, do not treat as findings):**
- H1: provider latency dominates end-to-end (near-certain by construction,
  unquantified per workload).
- H2: target-repo test-suite time is the second cost (unmeasured; varies
  by repo).
- H3: git subprocess + SQLite overhead is negligible (<1% at 4-way
  concurrency) — plausible, unmeasured.
- H4: Node startup matters for single-task CLI runs — unmeasured (likely
  ~100–300ms, irrelevant next to agent minutes but relevant for
  `status`/`show` UX).

## 5. Performance baseline and measurement gaps

- Closest thing to a baseline: M17's 180-run comparison (quoted above).
  No current-generation baseline exists for the M19–M23 engine line.
- Missing timing boundaries: process startup; per-git-call spans;
  worktree add/prune spans; DB query spans; prompt/context construction
  size (prompts are tiny — `real/prompts.ts` is 55 lines; context cost
  lives inside provider latency).
- Reproducibility: scale harness is deterministic-ish (seeded workloads,
  `survival.ts`, `aggregation.ts`); real-agent runs are inherently
  non-deterministic and provider-billed. Fair-comparison status: the
  M18 design doc is explicit about arm definitions and limitations —
  reuse its protocol rather than inventing a new one.
